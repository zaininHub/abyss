# 方案：分章节真实试玩测试体系（v4.2.5 反馈②）

> 承接用户反馈：「需要把真实测试方案改成，每个章节一个真实运行的测试，并且要把预计晋升携带到下个章节的资源作为输入，用来测试每个章节的可玩性、数值，当真实测试时，通过1~5 或M~N章时可以合并一起测试，并比对预期输入和真实输入的差别来校验准确性，注意适当引用浏览器测试」
>
> 设计原则（承接现有测试纪律）：真实浏览器 + 产品真实入口操作（不直接写 S 伪造进度）；每章一个独立可跑的测试单元；M~N 章合并时复用逐章产物（晋升携带资源）作为下一章的输入；预期/真实差值校验是核心验收。

## 一、目标与范围

- **章节定义**：主线 1~18 章（`CHAPTERS` 数字 id，线性链），番外 19~51 章不入体系（无晋升节奏、门槛为长线资产累计，可玩性由 30 天长跑兜底）。
- **每章一测**：`tests/chapters/ch{N}-playthrough.mjs` —— 以「第 N 章开局时的跨局资产」为输入，真实浏览器内跑完「从第 N 章开局 → 达成第 N+1 章条件并真实推进」的全过程。
- **合并跑法**：`tests/chapters/run-range.mjs --from M --to N` —— 顺序执行 chM → chN，把每章结束时（晋升结算后）的跨局资产快照作为下一章的输入种子；同时比对「预期携带」与「真实携带」的差值。
- **预期输入**：由「章节预算表」声明——每章预期携带的跨局资源（ES / 职级点 / RP / DM / 成就 / 传承遗物 / 回响 / 家族升级 / 章节图鉴）的**类型与数量区间**；真实跑完后逐项比对，超差即 FAIL。

## 二、核心机制设计

### 2.1 章节切分锚点：晋升 = 章节边界

游戏机制：主线推进由「晋升次数」（第 2/7/8/13~15 章条件）与「本局产出」（第 3/10 章科技数、第 4/11/12 章 ES、第 5/9 章远征、第 6/16/17 章信仰）双线驱动，晋升是跨局资产（ES/职级点/RP 奖励/回响/遗物传承）的唯一结算入口。

**章节测试单元 = 一次晋升周期**：

- 输入：第 N 章开局时的跨局资产快照（`CROSS_RUN_KEYS` 全集 + 章节号 `chapter: N` + 驻留时间回拨已就绪）。
- 过程：真实浏览器加载该种子 → 自动玩家（复用 v3110 自动玩家范式：doClick / buyUpgrade / claimProject / doPrestige / AI 五开关）从第 N 章开局状态真实游玩 → 满足 `CHAPTERS[N+1].cond` 且驻留达标 → 帧系统真实推进到第 N+1 章 → 继续游玩直至第 N+1 章内完成一次「可晋升条件」（canPrestige）→ 真实 `doPrestige`。
- 输出：晋升结算后的跨局资产快照（= 第 N+1 章开局输入）+ 过程曲线（逐日 EP/CPS/晋升次数/章号）。

> 「从第 N 章开局跑到第 N+1 章内的晋升」天然覆盖了第 N 章的章节条件达成过程 + 第 N+1 章新解锁模块的初步可玩性；且与玩家真实节奏一致（晋升在章内发生，跨章推进由条件驱动）。

### 2.2 预期携带资源表（校验的核心）

`tests/chapters/budget.mjs` 声明每章的「预期晋升携带」：

```js
// 每章一条：从第 N 章跑完晋升后，跨局资产应达到的量级（用于下一章输入校验）
export const BUDGET = {
  // 第 1 章（开局 → 首次晋升）：首升需求 runEarned ≥ 3e9（prestigeNeed 基数），
  //   esGain = floor(sqrt(runEarned/2e7)) ≈ floor(sqrt(150)) ≈ 12 ES（±宽松区间）
  1: { minPrestige: 1, es: [8, 40], rp: [1, 60], note: '首升 3e9，ES ~12，RP 奖励 ~2-3' },
  // 第 2~18 章：prestigeNeed 按 index^1.5 幂律增长，ES/职级点按 runEarned 增长曲线给区间
  //   （区间宽度 ±50%，只拦「数量级错误」——硬编码精确值会随数值调参频繁碎裂）
  2: { minPrestige: 3, es: [20, 120], ... },
  ...
};
```

**校验规则**（跑完每章后比对）：

1. `prestige` 增量 ≥ `minPrestige`（章内至少完成声明的晋升次数）。
2. 跨局资源落在预算区间：ES、职级点增量、RP 奖励增量（晋升 RP + 章节馈赠 RP）。
3. `chapter` 真实推进到 N+1（帧系统 chapter 系统驱动，非测试直接写）。
4. `resDiscovered` 锚点递增不丢失（RP/ES/DM 等一旦点亮不回退）。
5. 差值报告：预期 vs 真实逐项列出（比例 + 绝对值），任一项超出区间 → 该章测试 FAIL 并输出偏差明细。

### 2.3 复用现有基础设施

| 基础设施 | 来源 | 复用方式 |
|---|---|---|
| 真实浏览器 + 时间虚拟化 | `v3110-30day-browser.mjs` 的 `boot()`（Date.now 注入 + `__tick` 驱动 + 清 interval） | 抽成 `tests/chapters/_boot.mjs` 共享模块，v3110 与分章节测试共用（v3110 保持行为不变，只改为 import 共享模块） |
| 自动玩家决策 | `__runBatch`（购买评分/晋升节奏/AI 补编/领任务） | 抽成 `_player.mjs`，按「章节目标」参数化：`{ goalChapter: N+1, maxDays: D }` |
| QA 钩子 | `window.__qa`（2939 行起已导出 doPrestige/canPrestige/computeCps 等） | 直接使用，不新增钩子（除非实施时发现缺口） |
| 章节推进真源 | 帧系统 `chapter` 系统（frameSystems.js:220）真实推进 | 测试只提供条件（资产达标 + 驻留时间），推进由产品代码完成 |
| 预算真源 | `prestigeNeed` / `esGain` / `prestigeRpGain`（economy.js） | 预算表注释里给出公式推导；区间由公式 ±50% 生成，不硬编码猜测值 |

### 2.4 时间预算（真实可跑性）

- 每章模拟天数：`maxDays = CHAPTERS[N+1].minDays + 缓冲 3~6 天`（第 2 章 minDays=5 → 最多 10 模拟天；18 章合计 ≤ 130 模拟天 ≈ 30 天推演的 4 倍时长）。
- 单章真实耗时：v3110 的 30 天 ≈ 19 分钟（v3129 终章回放实测），即 ~38s/模拟天 → 单章 6~10 分钟，全 18 章顺序跑 ≈ 2~2.5 小时。
- **合并窗口提速**：M~N 合并跑时，章间**不重启浏览器**——晋升结算后直接在同一页面继续下一章（省去 boot 开销）；仅比对点落盘快照。
- **按需运行**（用户纪律）：默认不跑；「数值测试」时跑目标章 `run-range.mjs --from N --to N`；「全量测试」时 `--from 1 --to 18` 一把跑完。

### 2.5 报告与差值校验输出

每章产出 `tests/chapters/reports/ch{N}-report.json`：

```json
{
  "chapter": 3,
  "inputSnapshot": { "es": 12, "prestigePoints": 2, "chapter": "3", ... },
  "expected":   { "es": [20, 120], "minPrestige": 2 },
  "actual":     { "es": 34, "prestigeDelta": 3, "chapter": "4" },
  "deviations": [],
  "daily": [{ "day": 1, "ep": "...", "cps": "...", "chapter": "3" }, ...],
  "verdict": "PASS",
  "elapsedSec": 412
}
```

控制台逐章输出一行结论；全量跑完输出汇总表（章节/结论/耗时/最大偏差项），任何一章 FAIL 时汇总表置顶标红。

## 三、文件结构

```
tests/chapters/
├── _boot.mjs          # 共享：浏览器启动 + 种子注入 + 时间虚拟化（从 v3110 抽取）
├── _player.mjs        # 共享：自动玩家（目标驱动参数化）
├── _snapshot.mjs      # 共享：跨局资产快照/恢复（CROSS_RUN_KEYS 全集 + 比对工具）
├── budget.mjs         # 章节预算表（预期携带声明 + 公式注释）
├── run-range.mjs      # 入口：--from M --to N，顺序跑章并链式传递快照
└── reports/           # 逐章 JSON 报告（gitignore，不进仓库）
```

- `ch{N}-playthrough.mjs` 独立文件方案被合并跑法替代：逐章逻辑内聚在 `run-range.mjs` 的单章执行函数中（每章一个函数调用），避免 18 个高度雷同的文件维护漂移——**「每章一个测试」体现在报告与预算表条目上，而非物理文件**。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 中后段章节（4/11/12 章 ES 门槛、16/17 章信仰门槛）单章模拟天数过长 | 预算表允许声明 `carryBoost`：模拟「上一章晋升已携带的 ES 直接垫高起点」，驻留天数照常真实跑（时间门控不绕过）；单章上限 20 模拟天，超时判「预算不可达」FAIL 并输出瓶颈资源曲线 |
| 自动玩家在晋升天赋选择上摇摆 | 固定天赋序列（如 rich → legacy 交替），预算表注释声明假设 |
| 晋升 10% 随机信仰扰动预算 | 快照比对只看「区间 + 单调性」，随机项（faith/事件）不入预算校验 |
| 分支故事线（6A/7A…）干扰主线判定 | 种子固定 `storyline: 'default'`；岔路口在 5 章后选择中立（crossroad open 不锁定），预算表注明该假设 |
| 时间虚拟化与真实浏览器交互漂移 | 全程复用 v3110 已验证的 `__vt/__tick` 机制，不发明新机制 |
